Schema (compact form):
ReactionRecord = {file_name: str, reactions: [Reaction]}
Reaction       = {reaction_id: "<n>_<m>", reactants: [Compound], products: [Compound],
                  conditions: [Condition], additional_info: [str]}
Compound       = {smiles: str|null, label: str|null, uncertain: bool, bbox: [int,int,int,int]|null}
Condition      = {role: <enum>, text: str, smiles: str|null, bbox: [int,int,int,int]|null}

Allowed condition.role values (and ONLY these): {condition_role_enum}

Rules:
- file_name MUST be exactly "{file_name}".
- reaction_id format is "<scheme>_<variant>", e.g. "0_1", "0_2", with variant starting at 1. Each R-group variant becomes its own reaction entry with a unique reaction_id.
- For substrate-scope figures, EACH reaction entry must contain the SPECIFIC variant SMILES, not the bare wildcard template:
  * If rgroup_substitution emitted per-variant `reactant_smiles` and `product_smiles`, use those — one variant per reaction entry.
  * Do NOT repeat the same `*`-bearing template SMILES across all reactions. That is wrong.
  * Each variant's reactant in the JSON should be the substituted reactant_smiles for that variant; same for product.
- ENUMERATION COMPLETENESS — CRITICAL:
  * If rgroup_substitution listed N variants, emit EXACTLY N entries in `reactions[]`. Not 1 entry with N products. Not 2 entries summarising. N entries.
  * Each variant gets its own reaction_id ("0_1", "0_2", …, "0_N"), its own one-element `products: [{...}]` list (one product per entry), and its own one-element `reactants: [{...}]`.
  * Conditions, additional_info, and the second reactant (e.g. the imine partner shared by all variants) are duplicated across all N entries — that is correct and intended.
  * Do NOT pack multiple variant SMILES into a single reaction's `products` array. `products` should hold one item per reaction, not all variants of a substrate scope.
  * If molecular_recognition listed M concrete substrate-scope products and rgroup_substitution missed some, fall back to one reaction entry per molecular_recognition product. Same rules: one entry per variant, one product per entry.
- TABLE-ROW / ENTRY FAN-OUT — CRITICAL:
  * condition_interpretation emits ONE [FINDINGS] card per distinct `applies_to:` value. The values look like:
    - `applies_to: scheme_*` — the figure's generic template, often with placeholder values (`solvent="solvent"`, `temperature="temp."`).
    - `applies_to: entry N` / `row N` / `compound N` — a specific table row with concrete values (`solvent="toluene"`, `temperature="80"`).
  * If condition_interpretation emits a template card plus N row cards (N ≥ 1), emit EXACTLY N reaction entries — one per row card. Do NOT emit a separate "template" reaction. The template card is a source of invariant conditions, not its own reaction.
  * Reaction-id convention for table fan-out: row N → reaction_id "0_N". So a 13-row table produces reaction_ids "0_1", "0_2", ..., "0_13" (no leading scheme entry).
  * Each row entry's `conditions` list MERGES the template card's invariant conditions (e.g. "5 Å MS", "12 h", "1 equiv" loadings, generic catalyst-loading "5 mol%") WITH the row-specific conditions (catalyst identity, solvent, temperature, yield). Do NOT keep the template's placeholder values (`solvent="solvent"`, `temperature="temp."`) in any row entry that has concrete values from the row card.
  * Each row entry's `reactants`/`products` use the template SMILES — or, if the row's substrate column names a labelled compound (e.g. "1a", "1b") that rgroup_substitution or molecular_recognition has resolved to a substituted SMILES, use that resolved variant per row.
  * Add a one-line `additional_info` per row summarising the row, e.g. "entry 6: substrate 1b, catalyst D, toluene, 65 °C, 96% yield".
  * Most common failure mode (do NOT do this): collapsing multiple `applies_to` cards into a single reaction whose `conditions` list is a flat union of every card. The result has placeholder values like `solvent="solvent"` AND concrete values like `solvent="toluene"` side by side — that is wrong.
  * If condition_interpretation emits exactly 1 card (no fan-out present), produce 1 reaction as usual.
- Yields go under conditions with role="yield". Do NOT put yields in additional_info.
- "X mol%" / "X equiv" loadings → role="loading", not role="reagent".
- ee → role="ee". dr → role="dr". Pressure → role="pressure".
- If a SMILES is uncertain, keep it in `smiles` and set the compound's `uncertain` field to true.
- If a value cannot be determined, omit the optional field rather than inventing data.
- Conditions without a SMILES representation set `smiles` to null (or omit it).
- Do not introduce fields not listed above (the schema is `extra="forbid"`).
- NEVER write a SMILES with `[*:N]` markers (e.g. `Cc1ccc([*:1])cc1`) into a `smiles` field. Those are raw R-fragments returned by `derive_substituents`; they must be fused into a template via `apply_substituents(template_smiles, r_assignments)` BEFORE going into the JSON. If the validator rejects a SMILES for containing `[*:N]`, the fix is "call apply_substituents on it", not "delete the field".
- BBOX PASS-THROUGH: when a [FINDINGS molecular_recognition] or [FINDINGS condition_interpretation] card includes a `bbox: [x1,y1,x2,y2]` line for an entry (these come from MolDetect and OCR region detection), copy that bbox verbatim into the matching Compound or Condition you emit. Match by label (for compounds) or by `applies_to:` row + role text (for conditions). If no bbox was reported for an entry, omit the field or set `bbox: null`. Do NOT invent bboxes or carry one entry's bbox over to a different entry.
